# ZQ_GEMM 多内核 + 自动选路（设计提案）

- 日期：2026-10-01
- 起因：单核性能必须全方位逼近 MKL，多核差距可接受。是否可以通过"写很多种
  kernel + 按形状自动选路"达成？
- 结论：**可以，而且基础设施已经有一半**。缺的是"决策输入"和"机器自适应"。

---

## 一、现状：变体生成了，分发却只用了 4 个

`zq_gemm_32f_align_c_asm.c` 里 `ZQA_DEFINE_KERNEL(FNAME, MB, NB)` 宏已经能生成
任意 MB×NB 的分块驱动，当前生成了 7 个：

| 变体 | 之前是否被调用 |
|---|---|
| k1n4 / k1n8 / k2n4 / k2n8 / k4n4 / k4n8 / k8n4 | k1n4、k2n8、k4n4 **从未被调用** |

而顶层分发（`zq_gemm_32f_asm_mblocks`）只按 **M** 选：M≥8 用 M8_N4，剩 4 行用
M4_N8，剩 2 行用 M2_N4，剩 1 行用 M1_N8。**N 和 K 根本不进决策**。

底层的 5 个微内核（`core_m2n4` / `core_m1n8` / `core_m1n4` / `core_m4n1` /
`core_m1n1`）是按 K 方向做 ymm 累加 + 水平归约的，这是"寄存器分块"维度；
上层的 MB×NB 是"访存量"维度。两个维度是**正交**的，理想情况应该二维联合选择。

---

## 二、第一步增量（本次已做）：让 N 进决策

`M4_N8` / `M2_N4` / `M1_N8` 在 **4 ≤ N < 8** 时是错的：NB=8 而列数不够 8，
一个整块都凑不齐，全部落到标量尾部，比 NB=4 更慢。

改成 `wide_n = (N >= 8)` 时才用 NB=8，否则用 NB=4。顺带把三个从未被调用的
变体（`M1_N4` / `M2_N8` / `M4_N4`）接上了。

**性能实测**（`tools/bench_gemm_ab.py`，交替 5 轮，阈值 8%）：

```
64 个形状里：A 更快 1 个，A 更慢 2 个，61 个在噪声内
```

**在噪声内，不算提速**。原因也清楚：N 落在 4~7 的形状在 64 形状里只有
`5x7x3`、`7x5x13` 这几个，都是 2~5 GF/s 量级的小形状。

这一步的价值在结构而不是速度：它把"分发只看 M"这个缺陷改成了"分发看 M 和 N"，
K 的接入就只是再加一个条件；而且**没有引入回归**（3 个变动的形状都在噪声内）。

## 三、完整的选路设计

### 3.1 值得写的 kernel 家族

| 家族 | 适用条件 | 机理 |
|---|---|---|
| **A. K 向量化的寄存器分块**（现有） | K ≥ 8 | 每个累加器持有一条长度 K 的点积，末尾水平归约。FMA/load 比随 MB×NB 增大 |
| **B. N 向量化 + B 打包**（**已实现**） | K < 8 | 把 B 打包成 `[K][nc]`（同一 k 的所有列连续），一次出 8 列，C 只写一趟 |
| **C. K=1 外积特化**（**已含在 B 里**，`if (K==1)` 走赋值分支） | K == 1 | `C = a ⊗ b`。A 的标量只广播一次，之后全是连续 load + FMA + store，指令数可以做到 0.75/8 输出 |
| **D. N=1 专列**（现有 `core_m4n1`） | N == 1 | 4 行共享一次 b 向量加载 |
| **E. 大 MB 变体** | M 很大、B å¤ç¨æ¶çé« | MB=16/32，靠更多寄存器换更少的 B 重读 |

**关键约束（踩过的坑）**：`Bt` 是 **N×K 行主序**，`Bt[j][k] = Bt[j*ldb+k]`，
相邻列在内存里差 `ldb` 个 float 而**不是相邻**。所以家族 B/C 必须先打包；
直接沿 N 向量化会得到 8 个结果里 7 个错的、且**不崩溃**的输出。

### 3.2 决策应该看什么

按影响从大到小：

1. **K** —— 决定用家族 A 还是 B/C。K < 8 时家族 A 的 K 循环一次都不进，
   等于把 C 清零再标量补加。**这一族已在 2026-10-01 实现（家族 B+C 合并成一条
   "打包 B + 沿 N 算"的路径），asm/MKL 从 47%~51% 提到 103%~152%。**
   剩下的空白是 K ∈ [8, 32)：`k8 = 1~3`，K 循环能进但只跑 1~3 轮，
   19 条指令的水平归约固定开销摊不掉（`313x32x28` 仍 28%）。
2. **N** —— 决定 NB=4 还是 NB=8（≥8 才划算），以及 N=1 是否走家族 D。
3. **B 的缓存占用** `N*K*4` —— 决定要不要 N 方向分块（本次已加：> 256KB 就切）。
4. **M** —— 决定 MB，以及 B 面板能不能在 M 方向复用。
5. **M/N 的相对大小** —— 实测瘦长形状（行>>列、列>>行）汇编版反超 MKL 30%~56%，
   方阵落后 7%。这个差异大到值得进决策表。
6. **对齐**（`align_type`）—— 已经在 `align_mode = min(源, 目标)` 里处理。

### 3.3 分层结构

```
auto_asm(M,N,K,…)
 ├── N < 4?            → ncol 专列
 ├── K ≤ 8?            → 打包 B + N 向量化行内核（家族 B/C）  ← 缺口
 ├── B 装不下 L2?       → N 方向分块
 └── 每个 C 块 (MB×NB) → 按 (M,N,K) 从候选里选一个
```

前三层是**确定性规则**（能推理出来），第四层是**需要实测**的部分。

## 四、不同机器怎么自动选到最优

### 4.1 核心思路：**不要写死表格，在目标机器上现测**

写死的查表（"如果 CPU 是 Zen3 就走路径 X"）注定在别的机器上不对：
同代不同 SKU 的 L2 大小、内存带宽、频率特性都不同。

正确做法是**运行时自测**：

```
首次遇到某个"形状桶"(M,N,K 分桶) 时：
    对每个候选 kernel:
        用小块合成数据跑 R 轮，记录每轮耗时
    取每个候选的**中位数**，选最小的
    把结果缓存进 hash 表
    之后同桶直接命中
```

这样"针对本机最优"是自动成立的，换机器不用改代码。

### 4.2 三个必须处理的工程问题

**① 分桶**：不能按 (M,N,K) 精确匹配（形状几乎不重复）。按
`M ∈ {1,2,4,8,16,32,...}` 取最近的 2 的幂、`N`/`K` 同理分桶，
桶内用该桶的最小值代表。桶数控制在几百量级。

**② 启动开销**：调优本身要花时间。约束：
- 每个候选只跑很小的合成数据（比如 64×64×64），不碰用户的真实缓冲；
- 候选数 ≤ 8，轮数 R ≤ 5；
- 结果落盘到用户目录（按 `CPU 型号 + 编译器 + 编译选项` 命名），
  二次启动直接读表；
- 环境变量 `ZQ_GEMM_NO_AUTOTUNE=1` 可关掉，退回确定性规则。

**③ 线程安全**：自测缓存用函数内 `static` + 初始化即线程安全（C++11 magic static），
或者显式 `std::once_flag`。自测过程本身不能被多线程同时进入。

### 4.3 本项目特有的硬约束：**噪声是单边的，必须用中位数**

这一条是本机实测逼出来的，也是整个自测方案能不能用的关键：

- 空对照（同一份代码跟自己比）显示，本机 GEMM 读数**噪声下限约 7%**，
  5 轮里仍有 7/64 个形状出现 >3% 的假差异。
- 噪声**单边**：慢轮次会把整轮拖慢，快轮次不存在。
  → 候选用**最大**会让"某轮恰好顺风"的候选胜出；
  → 候选用**中位数**才稳（但仍然偏保守，因为整轮偏慢时会拖垮中位数）。

所以自测的判据是：**中位数差 < 噪声下限（7%）就视为打平，取更简单的那个候选**。
这条比"精确挑出最快的"更重要 —— 挑错在这个噪声水平上比挑对更糟。

本机 WSL 里没有 `perf`、也没有锁频权限，无法把噪声进一步压下去。
如果目标机器上能绑核 + 锁频（`taskset` / `cpupower`），同样的自测方案
可以把判定阈值降到 2% 以下，区分度会好很多。

## 五、建议的推进顺序

| 步骤 | 内容 | 理由 |
|---|---|---|
| 1 | **N 进决策**（本次已做） | 结构性改进，零风险，立刻让三个死变体上线 |
| 2 | **先把 K ≤ 8 的时间花在哪测出来** | 这一族是唯一比 intrinsic 还慢的（0.79~0.82×）、比 MKL 慢一半的。之前两次尝试都是"按 uop 估算设计 → 实测没收益"，根因是没测清楚 |
| 3 | 家族 B（打包 B + N 向量化），但**只在测完之后**做 | 这次要有计时探针分辨"打包时间 / 行内核时间" |
| 4 | 家族 C（K=1 特化） | 512x512x1 的理论上限是 C 的写入带宽，MKL 已经打满了 |
| 5 | 自测选路框架 | 有了 2~4 的多个候选才值得建；框架本身要按 4.3 的噪声规则设计 |

**第 2 步是阻塞项**：没有可观测性之前再做算法改动，大概率重复"设计得对、
实测没收益"的老路。

## 六、与多核的关系

本次实现的手写 GEMM 内核是**单线程**的（没有 OpenMP）。ZQCNN 的多核并行
在**层一级**（MTCNN 的 `_compute_Pnet_multi_thread`、SSD 的 im2col + GEMM 外层等），
不在这个 GEMM 里。

因此：
- **单核**：本文件讨论的范围，也是要求"全方位逼近 MKL"的部分。
- **多核**：本 GEMM 单线程 vs MKL 全线程，差距约等于核数倍率。按当前约定可以接受。

**本机无法测多核 MKL**：`mkl_intel_thread.3.dll` 依赖 `libiomp5md.dll`，
而该文件不在 `3rdparty/mkl_runtime/win/` 下，多线程模式进程直接起不来
（`SampleGEMMCompare --mt` 返回 127）。所以多核一栏在本报告中只有定性说明，
没有数字。补上 `libiomp5md.dll` 即可测量。
